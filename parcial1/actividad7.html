Objetivo del laboratorio

Leer el contenido de /etc/passwd explotando el parámetro filename del endpoint de imágenes, que no aplica ninguna validación sobre la ruta recibida.

Tipo de explotación: Path traversal directo (secuencias relativas)

CWE-22: Improper Limitation of a Pathname to a Restricted Directory

Contexto y reconocimiento previo

Antes de intentar explotar nada, lo primero fue identificar dónde la aplicación acepta un input que después usa para leer un archivo del servidor. La tienda del laboratorio ("We Like To Shop") muestra productos con imagen, y cada imagen se carga con una petición del tipo:

GET /image?filename=13.jpg HTTP/2

Ese parámetro filename es la pista clave: el nombre sugiere directamente que el servidor está usando ese valor para localizar un archivo en disco. Cualquier parámetro con nombres como filename, file, path, doc, document, folder o img es candidato natural a probar por path traversal — es el primer patrón que se busca al hacer reconocimiento de una aplicación.

La hipótesis de trabajo fue: si el servidor arma la ruta final como /var/www/images/ + valor de filename, sin sanitizar ese valor, entonces meter secuencias ../ debería permitir "salirse" de la carpeta de imágenes.

Explicación técnica de la vulnerabilidad

La aplicación arma la ruta del archivo concatenando directamente el valor de filename a un directorio base (algo como /var/www/images/), sin sanitizar secuencias ../. Al subir tres niveles de directorio con ../../../ se llega a la raíz del sistema de archivos, desde donde se puede referenciar etc/passwd directamente.

Por qué existe esta falla: en pseudocódigo, el backend probablemente hace algo equivalente a:

ruta_final = "/var/www/images/" + request.get("filename") return leer_archivo(ruta_final)

No hay ningún paso intermedio que verifique que ruta_final sigue apuntando dentro de /var/www/images/. El sistema operativo interpreta ../ como "sube un nivel", así que la concatenación de strings termina resolviendo una ruta completamente distinta a la que el desarrollador tenía en mente.

Por qué tres ../ y no otro número: en este laboratorio no hace falta calcular la profundidad exacta del directorio base — con tres repeticiones se garantiza llegar hasta la raíz (/) del sistema de archivos sin importar si /var/www/images/ tenía 2 o 3 niveles; una vez en la raíz, cualquier ../ adicional simplemente no tiene efecto (no se puede subir más allá de /), por lo que sobrepasar la cantidad necesaria no rompe el payload.

Procedimiento paso a paso

  • Paso 1. Entrar al lab y activar Intercept on en Burp Suite (pestaña Proxy). Por qué: sin interceptar, el navegador arma y envía la petición completa (headers, cookies de sesión, etc.) sin darnos oportunidad de modificarla antes de que salga. Interceptar la "congela" a mitad de camino.
  • Paso 2. Hacer clic en cualquier producto de la tienda para que el navegador pida su imagen. Por qué: es el disparador natural que hace que el navegador arme la petición /image?filename=... que queremos interceptar — no hay forma de "adivinar" esa URL sin verla generarse primero.
  • Paso 3. Cuando Burp intercepte GET /image?filename=N.jpg, mandarla a Repeater (clic derecho → Send to Repeater). Por qué Repeater y no editar la URL a mano: Repeater conserva automáticamente todos los headers originales (cookie de sesión, user-agent, referer) que la aplicación podría estar validando, y permite reenviar la misma petición las veces que haga falta sin repetir el flujo de intercepción cada vez.
  • Paso 4. En Repeater, sustituir el valor de filename por el payload. Por qué solo se cambia ese parámetro: es el único campo bajo control del atacante que termina siendo usado para localizar un archivo en disco; tocar cualquier otro header no tiene efecto sobre la vulnerabilidad.
  • Paso 5. Enviar (Send) y revisar que el Response devuelva el contenido de /etc/passwd. Qué confirma esto: que el servidor sí concatenó el payload sin sanitizarlo y que el sistema operativo resolvió la ruta hasta un archivo fuera del directorio de imágenes esperado.
  • Paso 6. Confirmar el badge "Lab solved" en la esquina superior derecha del navegador. Por qué: es la validación automática de PortSwigger de que la explotación fue exitosa y completa, más allá de que el Response "se vea bien".

Payload utilizado

GET /image?filename=../../../etc/passwd HTTP/2

Explicación del payload

Cada ../ sube un nivel de directorio; tres repeticiones son suficientes para llegar a la raíz desde /var/www/images/ y acceder a /etc/passwd. El servidor no valida ni filtra esta secuencia en ningún punto.

FragmentoQué hace
filename=Parámetro vulnerable que el backend usa directamente para construir la ruta del archivo a servir.
../ (×3)Cada una sube un nivel de directorio desde el punto de partida (/var/www/images/) hasta llegar a la raíz /.
etc/passwdRuta relativa a la raíz del archivo objetivo — el listado de cuentas de usuario del sistema operativo.

Análisis de la respuesta obtenida

El servidor respondió con HTTP/2 200 OK y, en vez de una imagen, el Content-Type siguió marcado como image/jpeg pero el cuerpo de la respuesta trae texto plano — otra señal de que el servidor entrega ciegamente el contenido del archivo resuelto, sin verificar que en realidad sea una imagen. El contenido devuelto tiene esta forma:

root:x:0:0:root:/root:/bin/bash daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin ... academy:x:10000:10000::/academy:/bin/bash

Cada línea de /etc/passwd sigue el formato usuario:x:UID:GID:comentario:home:shell. Aunque en sistemas modernos las contraseñas reales ya no viven aquí (están en /etc/shadow, no accesible sin privilegios), este archivo sigue siendo información sensible porque revela:

Dato expuestoPor qué importa
Nombres de usuario reales (ej. peter, carlos, academy)Da al atacante una lista de cuentas válidas para intentar fuerza bruta o phishing dirigido.
Shells asignados (/bin/bash vs /usr/sbin/nologin)Indica qué cuentas tienen acceso interactivo real al sistema y cuáles son solo cuentas de servicio.
Estructura de directorios homeConfirma rutas del sistema de archivos útiles para futuros payloads de traversal más dirigidos.

Impacto y riesgo real

En este laboratorio el objetivo fue /etc/passwd porque es el estándar académico para demostrar la vulnerabilidad de forma inequívoca, pero el mismo parámetro sin sanitizar permite leer cualquier archivo al que el proceso del servidor web tenga permiso de lectura. En un sistema real, esto podría incluir:

  • Archivos de configuración con credenciales de base de datos (ej. config.php, .env, web.config).
  • Claves privadas SSH (~/.ssh/id_rsa) si el proceso tiene permisos sobre el home de algún usuario.
  • Código fuente de la aplicación, revelando lógica de negocio y posibles vulnerabilidades adicionales.
  • Logs del servidor, que pueden contener tokens de sesión o datos de otros usuarios.

Es decir: la severidad real de un path traversal no depende del archivo usado para la prueba de concepto, sino de qué tan sensible es el archivo más comprometedor que el atacante logre alcanzar con el mismo parámetro.

Mitigación recomendada

⚠ CONTROL DE SEGURIDAD

Nunca construir rutas de archivo concatenando input del usuario directamente. Usar un mapa de identificadores a archivos permitidos (whitelist), o validar la ruta canónica resultante contra el directorio base permitido.

En términos prácticos, la corrección para este caso específico sería reemplazar la concatenación directa por una de estas dos estrategias:

EstrategiaCómo se vería aquí
Whitelist de IDsEn vez de recibir un filename libre, recibir un id numérico y mapearlo internamente a un nombre de archivo fijo predefinido por el servidor (el usuario nunca controla el string de la ruta).
Validación de ruta canónicaResolver la ruta final con getCanonicalPath() (o equivalente) y rechazar la petición si el resultado no empieza con /var/www/images/.
